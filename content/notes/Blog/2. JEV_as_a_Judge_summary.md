# JEV-as-a-Judge: เมื่อ AI Judge ไม่จำเป็นต้องคิดทุกข้อเอง
$$ \frac{x^2 + 1}{y - 3} $$
> **Paper:** Yubo Li, Yidi Miao, Ramayya Krishnan, Rema Padman  
> **Title:** *JEV-as-a-Judge: Accept When Confident, Escalate When Unsure*  
> **arXiv:** https://arxiv.org/abs/2609.26550  
> **Version ที่สรุป:** v3, 29 September 2026

## TL;DR

ปัญหาของ **LLM-as-a-Judge** คือ แม้ LLM จะประเมินคำตอบได้ดี แต่การให้โมเดล reasoning ขนาดใหญ่ตัดสินทุกตัวอย่างมีทั้ง **ค่าใช้จ่ายสูงและ latency สูง**

งานนี้เสนอแนวคิดที่น่าสนใจมากกว่า “สร้าง judge ที่เก่งกว่าเดิม” คือใช้ **JEV เป็น judge ด่านแรก** ซึ่งคืนเพียง **verdict + probability ของแต่ละ label** โดยไม่ต้อง generate rationale หรือคำอธิบาย จากนั้นใช้ probability สูงสุดเป็น **confidence**:

- ถ้า confidence สูง → เชื่อคำตอบของ JEV
- ถ้า confidence ต่ำ → ส่งต่อให้ reasoning LLM เช่น GPT-6

ดังนั้นเป้าหมายไม่ใช่ให้ JEV ชนะ LLM ทุกกรณี แต่ให้มันตอบคำถามว่า

> **“ข้อนี้ฉันมั่นใจพอที่จะตัดสินเองหรือควรส่งต่อ?”**

ผลทดลองพบว่า JEV ทำได้ใกล้ GPT-6 ในงานที่ verdict สามารถอ่านจากข้อความได้โดยตรง แต่จะอ่อนลงในงานที่ต้อง “คิดหา” คำตอบ เช่น math, code และ logic อย่างไรก็ตาม error จำนวนมากอยู่ในกลุ่มที่ JEV มี confidence ต่ำ ทำให้สามารถใช้ confidence เป็นตัว routing ได้

ใน held-out preference pairs จำนวน 1,610 คู่ cascade ที่ใช้ JEV → GPT-6 ทำ accuracy สูงกว่า GPT-6 เดี่ยว **0.9 percentage points** ขณะที่ใช้ค่าใช้จ่ายเพียง **41%** ของ GPT-6 และในการทดสอบ workload ใหม่ 2 ชุด cascade ให้ accuracy เท่ากับ GPT-6 โดยส่งต่อประมาณ **74%** ของเคสและลดค่าใช้จ่ายประมาณ **25%**

# 1. แนวคิดของโมเดลเกิดจากอะไร?

## ปัญหา: LLM-as-a-Judge แพงเกินไปเมื่อใช้ใน scale ใหญ่

การประเมิน LLM แบบดั้งเดิมมี 3 ทางหลัก:

1. **Human evaluation** — คุณภาพดี แต่แพงและ scale ยาก
2. **Traditional metrics** เช่น BLEU — เร็ว แต่ต้องมี reference และไม่เหมาะกับ open-ended response
3. **LLM-as-a-Judge** — ยืดหยุ่นและเข้าใจ rubric ได้ แต่มีค่า inference และ latency สูง

โดยเฉพาะ reasoning model หากให้มันคิดทุกตัวอย่าง แม้ตัวอย่างนั้นจะง่ายมาก ก็ยังต้องจ่าย computation เพื่อหาคำตอบ

Paper จึงตั้งคำถามใหม่:

> เราจำเป็นต้องใช้ reasoning LLM กับทุกตัวอย่างจริงหรือ?

คำตอบของงานคือ **ไม่จำเป็น**

ถ้าเรามี judge ราคาถูกที่สามารถตัดสิน case ง่าย ๆ ได้ และที่สำคัญคือ **รู้ว่าตัวเองไม่มั่นใจเมื่อไร** เราสามารถใช้มันเป็น first stage แล้วส่งเฉพาะ case ที่ยากไปให้ model ที่แพงกว่า

# 2. JEV คืออะไร?

JEV ในงานนี้เป็น **decision-only judge**

แทนที่จะ generate:

```text
Candidate A is better because ...
Therefore, I choose A.
```

JEV คืนผลลัพธ์ประมาณ:

```text
A: 0.91
B: 0.06
C: 0.03

verdict = A
```

ให้

\[
q = \max_k p_k
\]


โดย `q` คือ probability สูงสุดของ label ที่ JEV เลือก และใช้เป็น **confidence**

ตัวอย่าง:

```text
A = 0.91
B = 0.06
C = 0.03
```

ดังนั้น

```text
verdict = A
confidence = 0.91
```

จากนั้นกำหนด threshold `τ`

```text
if confidence >= τ:
    accept JEV
else:
    escalate to stronger LLM
```

เช่น ถ้า `τ = 0.90`

```text
0.91 >= 0.90  → ใช้ JEV
0.72 <  0.90  → ส่งต่อ GPT-6
```

### จุดสำคัญ

JEV ไม่ได้ถูกเสนอใน paper ว่าเป็น reasoning model ตัวใหม่ที่ต้องเอาชนะ LLM ใหญ่ ๆ

สิ่งที่ paper ศึกษาคือ **decision-only interface + confidence routing**

และผู้เขียนระบุชัดว่าพวกเขาเน้นการวัด operating profile มากกว่าการเสนอ routing algorithm ใหม่

# 3. แล้วทำไม JEV ถึงเร็วและถูกกว่า LLM?

ต้องแยกเป็นสองประเด็น

## 3.1 JEV ไม่ต้อง generate explanation

LLM judge แบบ generative สามารถสร้าง rationale ก่อนตัดสิน เช่น:

```text
Let's analyze candidate A...
First...
Second...
Therefore...
```

แต่ JEV ต้องการเพียง structured decision:

```text
label A = 0.91
label B = 0.09
```

จึงไม่มี generation ของ reasoning text

ในระบบ evaluation ที่มีจำนวน judgment จำนวนมาก ความแตกต่างนี้มีผลต่อทั้ง **latency และ cost**

## 3.2 JEV ถูกออกแบบให้เป็น decision-only service

Paper ใช้ TypeSafe JEV ซึ่งรับ:

- natural-language instructions
- structured input
- allowed output type

และคืน probability ของ label โดยไม่มี generated text

สำหรับการทดลอง JEV 1.13.0 มีค่า input อยู่ที่ประมาณ `$0.042 / 1M tokens` และไม่มีค่า output ตามราคาที่รายงานใน paper

ดังนั้นเราไม่ควรตีความว่า:

> “JEV เร็วเพราะมี parameter น้อยกว่า LLM”

paper **ไม่ได้เปิดเผย architecture/parameter count ในระดับที่ทำให้สรุปแบบนั้นได้**

ข้อสรุปที่ปลอดภัยกว่าคือ:

> **JEV มี interface และ serving behavior ที่เน้น decision โดยตรง แทนการสร้างข้อความ reasoning**

# 4. JEV ทำงานกับ LLM Judge อย่างไร?

ภาพรวมคือ **Cascade**

```text
                  ┌───────────────┐
Candidate ───────►│      JEV      │
                  │ first-stage   │
                  └───────┬───────┘
                          │
                    confidence q
                          │
               ┌──────────┴──────────┐
               │                     │
            q >= τ                 q < τ
               │                     │
               ▼                     ▼
        Accept JEV verdict      GPT-6 / LLM Judge
                                      │
                                      ▼
                                Final verdict
```

แนวคิดนี้คล้าย **selective prediction / abstention**

โมเดลไม่จำเป็นต้องตอบถูกทุกข้อด้วยตัวเอง แต่ต้องสามารถบอกได้ว่า:

> “ข้อไหนฉันมั่นใจ และข้อไหนควรให้คนอื่นตัดสิน”

# 5. Benchmark วัดอะไรบ้าง?

Paper เปรียบเทียบ JEV กับ judge จำนวนมาก รวมทั้ง generative LLM และ reward models

ชุดหลักมี:

- RewardBench — 1,500 preference pairs
- JudgeBench — 350 preference pairs
- HaluEval — 3,000 evidence-grounded factuality judgments
- รวม public judgments หลัก 4,850 รายการ
- มี follow-up tests สำหรับ style, format, multi-choice และ natural prose
- มี blinded human adjudication ใน subset
- มี prospective live test บน workload ใหม่ 2 ชุด

---

## 5.1 Accuracy

ตัวชี้วัดพื้นฐานคือ:

\[
Accuracy = \frac{\text{จำนวนคำตัดสินที่ถูกต้อง}}
{\text{จำนวนตัวอย่างทั้งหมด}}
\]

สำหรับ pairwise judging จะดูว่า judge เลือกคำตอบที่ตรงกับ gold label หรือไม่

ผลรวม public judgments:

- JEV: อยู่ประมาณอันดับกลางของกลุ่ม LLM judges
- JEV ต่ำกว่า GPT-6 ประมาณ **1.7 points**
- แต่ JEV ถูกกว่าประมาณ **277×**
- median latency ประมาณ **0.15 วินาที**

ดังนั้นจุดขายหลักของ JEV ไม่ใช่ “accuracy สูงสุด” แต่คือ **accuracy ที่ดีพอเมื่อแลกกับ cost/latency ที่ต่ำมาก**

# 6. สิ่งที่น่าสนใจกว่า Accuracy: Confidence

ถ้า JEV แค่ถูกใน average แต่ไม่รู้ว่าตัวเองผิดเมื่อไร การเอาไปทำ cascade ก็ไม่มีประโยชน์

ดังนั้น paper จึงถามว่า:

> เมื่อ JEV บอกว่า “ฉันมั่นใจ” จริง ๆ แล้วมันถูกมากขึ้นหรือไม่?

## 6.1 Accuracy ตาม confidence

เมื่อ confidence สูงถึงอย่างน้อย `0.9`

JEV และ GPT-6 มี accuracy ใกล้กันมาก:

- JEV: **94.7%**
- GPT-6: **94.4%**

จาก 3,744 items

นี่เป็นหลักฐานสำคัญว่า confidence สามารถใช้เป็น signal เพื่อคัดว่า case ไหนควร accept ได้

---

# 7. Metric สำหรับวัดคุณภาพของ Confidence

Paper ไม่ได้ดูแค่ accuracy แต่ใช้ metric สำหรับ probability ด้วย

## 7.1 Brier Score

Brier score วัดว่า probability ที่โมเดลให้สอดคล้องกับผลลัพธ์จริงแค่ไหน

สำหรับ binary classification:

\[
Brier = \frac{1}{N}\sum_{i=1}^{N}(p_i-y_i)^2
\]

โดย:

- `p_i` = probability ที่โมเดลให้กับ event
- `y_i` = ผลจริง 0 หรือ 1

**ยิ่งต่ำยิ่งดี**

ตัวอย่าง:

```text
Model A: บอกถูก 90% และจริง ๆ ถูก → error = (0.90 - 1)^2
Model B: บอกถูก 99% แต่จริง ๆ ผิด → error = (0.99 - 0)^2
```

Brier จึงลงโทษโมเดลที่ **มั่นใจมากแต่ผิด** หนักกว่าการดู accuracy อย่างเดียว

---

## 7.2 AUROC สำหรับ Confidence

Paper ยังวัดว่า confidence สามารถใช้แยก:

```text
correct
vs
wrong
```

ได้ดีแค่ไหน

โดยใช้ confidence เป็น score สำหรับ error detection

\[
AUROC = P(score(correct) > score(wrong))
\]

โดยประมาณ:

- `0.5` = แยกไม่ออก
- `1.0` = แยกได้สมบูรณ์

สำหรับ JEV:

- RewardBench: **0.88**
- JudgeBench: **0.73**
- HaluEval: **0.83**
- pooled: **0.82**

จึงเห็นว่า confidence มี signal ค่อนข้างดี แต่ไม่ได้สมบูรณ์ โดยเฉพาะ benchmark ที่ต้อง reasoning มาก

# 8. Benchmark บอกอะไรเกี่ยวกับ “ความยาก” ของงาน?

นี่เป็น insight สำคัญที่สุดของ paper

JEV ทำได้ดีเมื่อคำตอบสามารถ **อ่านออกจาก text โดยตรง**

เช่น:

- ordinary preference
- safety
- evidence-grounded factuality
- chat quality

แต่ performance ลดลงเมื่อการตัดสินต้อง **derive/verify reasoning**

เช่น:

- expert knowledge
- mathematics
- programming/code
- logic puzzles

ในกลุ่มเหล่านี้ JEV ตาม GPT-6 ประมาณ **7–28 percentage points**

และมีอีกกรณีที่น่าสนใจ:

> ถ้าคำตอบผิดถูกเขียนมาอย่างละเอียดและดูน่าเชื่อ JEV สามารถถูกหลอกได้ง่ายขึ้น

ดังนั้น JEV เหมาะกับการเป็น **fast filter** มากกว่าการเป็น universal reasoning judge

# 9. Cascade Benchmark

จากนั้น paper ทดลองเอา JEV มาเป็น first-stage:

```text
JEV
 │
 ├── confident → accept
 │
 └── uncertain → GPT-6
```

บน held-out preference pairs จำนวน **1,610 คู่**

ผลของ frozen cascade:

- accuracy สูงกว่า GPT-6 เดี่ยว **0.9 points**
- ใช้ค่าใช้จ่ายประมาณ **41% ของ GPT-6**
- escalate ประมาณ **31% ของ pairs**

บน RewardBench:

- escalate ประมาณ 25%
- ใช้ค่าใช้จ่ายประมาณ 27% ของ GPT-6

บน JudgeBench ซึ่งเป็นงานที่ JEV อ่อนกว่า:

- ต้อง escalate ประมาณ 65%
- cascade ปิด gap จาก JEV เดี่ยวกับ GPT-6 ได้ประมาณ 94%

นี่แสดงให้เห็นหลักการสำคัญ:

> ถ้างานยาก JEV จะส่งต่อมากขึ้น แทนที่จะฝืนตัดสินเอง

---

# 10. Prospective Test: ทดสอบกับ workload ใหม่

เพื่อไม่ให้ผลดีเฉพาะ benchmark เดิม ผู้เขียนทำ pre-specified live test กับ workload ใหม่ 2 ชุด รวม **570 held-out pairs**

ใน workload นี้ JEV เดี่ยวตาม GPT-6 อยู่ประมาณ **14 points**

แต่เมื่อใช้ cascade:

- เลือก threshold จาก local labels ประมาณ 100 ตัวอย่างต่อ workload
- escalate ประมาณ **74%**
- accuracy ของ cascade **เท่ากับ GPT-6**
- ประหยัดค่าใช้จ่ายประมาณ **25%**

นี่สะท้อน trade-off ที่สำคัญ:

> ถ้า first-stage judge ไม่เก่งพอ ระบบไม่ได้ “หลอกตัวเอง” ว่าประหยัดได้ 90% แต่จะยอมส่งต่อมากขึ้นเพื่อรักษาความถูกต้อง

# 11. Applications ที่นำไปใช้ได้

## 11.1 LLM Evaluation Pipeline

เหมาะที่สุดสำหรับระบบที่ต้อง evaluate output จำนวนมาก เช่น:

```text
New model checkpoint
       │
       ▼
Generate 1M responses
       │
       ▼
JEV judge
       │
       ├── easy → accept
       │
       └── uncertain → GPT reasoning judge
       │
       ▼
Evaluation report
```

แทนที่จะใช้ GPT-6 judge ทั้ง 1 ล้านรายการ ก็ใช้ LLM ใหญ่เฉพาะส่วนที่ JEV ไม่มั่นใจ

---

## 11.2 RAG Evaluation

ตัวอย่าง metric:

- answer relevance
- groundedness
- factual consistency
- citation correctness

กรณีที่ evidence และ answer ทำให้ verdict เห็นได้ค่อนข้างตรงไปตรงมา JEV สามารถทำ first-pass evaluation ได้

ส่วน case ที่ evidence ขัดแย้งกันหรือจำเป็นต้อง reasoning ก็ escalate

---

## 11.3 Agent / Tool-use Evaluation

สำหรับ agent ที่มีจำนวน trajectory จำนวนมาก:

```text
Agent trajectory
      │
      ▼
JEV
      │
      ├── clearly successful → accept
      │
      └── ambiguous → reasoning judge
```

เหมาะกับการประเมิน:

- task success
- tool selection
- instruction following
- safety policy compliance

---

## 11.4 Regression Testing ของ LLM

เมื่อมี model version ใหม่:

```text
Model v1 → 100K outputs
Model v2 → 100K outputs

          ↓

       JEV Judge

          ↓
   ┌───────────────┐
   │ confident      │
   │ comparisons    │
   └───────────────┘
          │
   difficult cases
          ▼
      GPT Judge
```

ช่วยลด cost เมื่อ pipeline ต้องรันซ้ำทุกครั้งที่:

- เปลี่ยน checkpoint
- เปลี่ยน prompt
- เปลี่ยน RAG data
- เปลี่ยน agent workflow

# 12. ข้อจำกัดที่ต้องระวัง

Paper ไม่ได้บอกว่า JEV สามารถแทน LLM judge ได้ทั้งหมด

ข้อจำกัดสำคัญ:

### 1. Proprietary model

ทดลองกับ JEV รุ่นหนึ่ง และ architecture ภายในไม่ได้เปิดเผยทั้งหมด จึงไม่ควรสรุปว่า principle เดียวกันจะได้ผลกับ model อื่นทันที

### 2. ไม่เหมาะกับ reasoning-heavy tasks เสมอไป

Math, code, logic และ expert knowledge เป็นจุดที่ JEV ตาม reasoning judge ชัดเจน

### 3. Confidence ไม่ได้เชื่อถือได้ทุกสถานการณ์

โดยเฉพาะ:

- style-adversarial pairs
- reference-free prose

โมเดลอาจ **มั่นใจทั้งที่ผิด**

### 4. ต้อง calibrate threshold ตาม workload

ไม่ควรใช้:

```text
τ = 0.9
```

กับทุกงานโดยอัตโนมัติ

Paper แนะนำให้ใช้ local labeled examples เพื่อเลือก threshold และใช้ lower confidence bound เพื่อควบคุมความเสี่ยง

# 13. Takeaway สำหรับการนำเสนอ

ถ้าต้องสรุป paper นี้ใน 15 นาที สามารถเล่าเป็น 5 ประโยค:

> **1. ปัญหา:** LLM-as-a-Judge มี accuracy ดี แต่ reasoning ทุกครั้งแพงและช้า

> **2. แนวคิด:** ใช้ JEV เป็น decision-only judge ที่ตอบเฉพาะ verdict + probability

> **3. Key insight:** confidence ของ JEV สามารถบอกได้ระดับหนึ่งว่า case ไหนง่ายและ case ไหนควรส่งต่อ

> **4. Solution:** ใช้ JEV เป็น first stage และ escalate เฉพาะ low-confidence cases ไปยัง reasoning LLM

> **5. ผลลัพธ์:** บน held-out pairs cascade ทำ accuracy สูงกว่า GPT-6 0.9 points ที่ประมาณ 41% ของค่าใช้จ่าย และใน workload ใหม่สามารถ match GPT-6 ได้พร้อมลดค่าใช้จ่ายประมาณ 25%
